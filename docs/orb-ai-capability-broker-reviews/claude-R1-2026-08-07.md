## Summary position

**Recommend D1 = Yes**, with `claude-R1-C1` treated as a precondition on the
threat model rather than a later refinement.

The architecture is sound and the document is unusually disciplined about
evidence. Three things are notably right and should not be traded away in
revision: the Verified/Inferred/Not-yet-verified split in §3; the requirement in
§10 that *revoked credentials are tested to fail and active credentials tested
to succeed*, which is the exact control that would have caught a real defect
found on 2026-08-05; and §9's rule that transport success is not evidence of
persisted success.

My substantive concerns are one gap in the threat model, one missing decision
row, and one circularity in the acceptance test. The rest are refinements.

## Comments

### `claude-R1-C1` — **Blocker** (scope: §5 threat model, §6.2)

**The threat model covers an agent *reading* a credential store but not an
agent *writing its own authorization configuration*.**

§5 defends against "A client shell reading a credential store, environment,
process argument, temporary file, log, or inherited child environment." Reading
is only half the exposure.

**Evidence (verified, 2026-08-05/07 session):** Claude Code edited its own
`.claude/settings.json` — the file containing its `permissions.deny` rules —
using its ordinary Edit tool, and committed the result. That was done at Stan's
explicit instruction, so it demonstrates *capability*, not intent. The same
capability means an agent can in principle widen or remove its own guardrails,
and separately that anything stored in an agent-writable config path is
mutable by the agent, not merely readable.

This matters directly for D2/D9. If the MCP credential or its client config
lives anywhere the agent's own shell can write, then per-client revocation is
weaker than §7 implies: the client can potentially alter the local half of its
own enrollment.

**Recommendation:** extend §5 to defend against *client modification of its own
authorization or permission configuration*, and add a corresponding line to
§10: the server's view of a client's scopes must be authoritative and must
never be influenced by client-side configuration. Add a negative test in §13:
a client that locally alters its own config cannot thereby gain a scope the
server has not granted.

Labelled Blocker because it is cheaper to state now than to retrofit after
enrollment design is frozen in Phase A.

### `claude-R1-C2` — **Verified finding** (scope: §3, §6.2)

**§3's claim that the REST task API authenticates with a shared
`ORB_API_SECRET` is confirmed, and it fails closed.** `app/api/tasks/route.ts:12`
compares unconditionally:

```ts
if (request.headers.get('Authorization') !== process.env.ORB_API_SECRET) {
  return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
}
```

With the variable unset this still returns 401. A grep for conditional
secret guards across `app/` returns no other instances.

**Why this is worth recording:** on 2026-08-05 both cron routes used the
*conditional* form `if (process.env.CRON_SECRET && header !== ...)`, which
silently disabled authentication whenever the variable was absent — and it was
absent in production, leaving `/api/cron/reminders` (which sends push and email
to real users) open to anyone with the URL. That flaw had passed an ORB-374
review because the code *looks* like it authenticates. Fixed in v0.6.286.

**Recommendation:** the Capability Service is a new privileged production
surface (§15 acknowledges this). Add to Phase A a structural guarantee rather
than a coding convention — for example a startup assertion that required
secrets are present or the route refuses to register, so a misconfigured
deployment fails to serve rather than serving unauthenticated. §15's "must be
simpler and more rigorously tested" is true but is not a mechanism.

### `claude-R1-C3` — **Recommendation** (scope: §10, §16)

**No decision row governs the fate of the existing shared-secret REST path.**

§10 states "No shared `ORB_API_SECRET` for the new surface", which constrains
the new interface but leaves `/api/tasks` in place and unchanged. The net effect
of Phases A–E as written is that a safe path is *added alongside* the existing
one. Since §2 frames the problem as containment, an agent (or anything else)
holding `ORB_API_SECRET` retains the broader capability the broker is designed
to replace.

**Recommendation:** add a decision row — suggested **D15: disposition of the
existing `ORB_API_SECRET` REST surface** — with options such as retain for
non-AI integrations / restrict by scope / deprecate on a dated schedule after
Phase D. Note that Helm holds the coordinated `TODOS_API_SECRET` counterpart,
so this is cross-project and cannot be decided inside Orb alone.

### `claude-R1-C4` — **Inference** (scope: §13 step 8)

**The acceptance sequence verifies the broker using the broker.**

Step 8 has Claude Code "independently read the same todo, Knowledge entry, and
audit evidence through its own identity." That establishes cross-*client*
independence, which is real and worth having. It does not establish
independence from the component under test: both clients read through the same
Capability Service, the same authorization path, and the same sanitization
layer. A defect in the service — a mutation reported as persisted but rolled
back, a receipt generated before commit — could satisfy both readers.

**Recommendation:** add one verification step that does not traverse the
Capability Service, performed by Stan: a direct `psql` or Supabase-dashboard
read of the todo row, the Knowledge row, and the audit events. One query,
performed once, converts step 8 from consistency-checking into confirmation.

This mirrors §14's own principle ("one HTTP/MCP success is not evidence of
persisted success") — the same reasoning applies one level up.

### `claude-R1-C5` — **Question** (scope: §7.3, §8 `todo_close`)

**Does `todo_close`'s atomicity survive the Knowledge Repository moving?**

§7.3 and §8 require close to be one transaction spanning the todo mutation, the
audit write, and Knowledge entry creation. That is achievable today only because
the Knowledge Repository shares Orb's Supabase instance. Shared `AGENTS.md`
records that coupling explicitly as temporary: *"The Knowledge Repo currently
resides in Orb's Supabase instance for practical reasons. This is a temporary
coupling."*

If Knowledge moves to a dedicated database, a single transaction is no longer
available and the invariant in D8 silently degrades into two writes that can
diverge.

**Recommendation:** state the dependency in §7.3, and record the intended
behaviour if the stores separate — transactional outbox, or a compensating
action with an explicit reconciliation path. Cheaper to name now than to
discover when the move happens.

### `claude-R1-C6` — **Recommendation** (scope: §7.3, §13)

**Client-supplied idempotency keys do not protect against the failure mode the
threat model names.**

§5 defends against "A confused agent widening project scope or mutating the
wrong record." A confused or restarted agent retrying a semantically identical
operation will typically generate a *new* idempotency key, and replay
protection keyed on the client's own value will not fire. The §13 replay test
("replaying each mutation idempotency key returns the original receipt")
verifies the honest-client path only.

**Recommendation:** add a short server-side duplicate-detection window on a
normalized tuple — client, capability, resolved target or title — that returns
the existing receipt or a typed `duplicate_suspected` error. Add a negative
test: the same logical create submitted twice under *different* keys does not
produce two todos.

### `claude-R1-C7` — **Recommendation** (scope: §7.1, §13 negative tests)

**No negative test covers client impersonation, though §5 defends against it.**

§7.1 correctly says model name/version is recorded but not trusted for
authorization. The stronger requirement is that the *client identity* written to
audit derives from the presented credential and never from request payload
fields.

**Recommendation:** add negative tests — a request from `codex` cannot cause an
audit record attributed to `claude_code`; a client cannot read another client's
audit rows or enrollment record; supplying a conflicting client identity in the
payload is rejected rather than silently ignored.

---

### `claude-R1-C8` — **Recommendation** (scope: §4, §8)

**The capability contract overlaps the existing conversational Orb tool
contract, and no decision assigns a single source of truth.**

`lib/orb-contract.ts` is currently documented in `AGENTS.md` as "the single
source of truth for what Orb can and cannot do," with `create_todo`,
`query_todos`, `update_todo`, `delete_todo`. §8 defines a parallel set with
different names and semantics (notably `todo_close` as a distinct operation,
which the conversational contract lacks, and no `delete`).

§4's goal — "Use the same domain services … wherever their authorization
semantics match" — addresses the *service* layer but not the *contract* layer.
Two contracts describing todo closure invites divergence.

**Recommendation:** add a decision on whether `lib/orb-contract.ts` becomes the
shared declaration for both surfaces or the capability contract is deliberately
separate with a documented mapping. If shared, note that the AGENTS.md eval rule
then attaches: a change to a shared tool contract requires matching cases in
`scripts/eval-cases.ts`. §14 currently reasons about this correctly for the
no-overlap case only.

### `claude-R1-C9` — **Recommendation** (scope: §8 `knowledge_search`, §15)

**Default `knowledge_search` to metadata-only, with content on explicit
request.**

§8 already allows "content only when requested", which is the right instinct;
recommend making it the enforced default rather than an option. Two reasons.
§15 flags that complete Knowledge access may expose sensitive historical content
even with credentials hidden — a metadata-first default bounds that by
construction. And it is measurably the cheaper interaction pattern: in the
2026-08-05 session the effective sequence was a title/ID listing across the
repository, then exactly one full fetch of the single relevant entry.

Same reasoning supports a low server-set default limit, which §7.3 already
requires.

### `claude-R1-C10` — **Verified finding** (scope: §3 "Not yet verified", first bullet)

Partial evidence toward "Which current Codex and Claude Code credential stores
are inaccessible to their general-purpose shells on this Mac," from the
2026-08-05/07 session:

- **The encrypted secret bundle is reachable but not readable.** Claude Code's
  shell can `ls` and `openssl` against
  `/Users/stanleybaptista/Project-secrets/orb-secrets/orb.env.enc`, but every
  decryption required Stan to type the passphrase interactively. The agent never
  obtained a plaintext value. Containment behaved as ORB-375 intended.
- **Variable names were listable without exposing values** (`… | cut -d= -f1`),
  which is a useful pattern for future diagnostics and confirmed that
  `CRON_SECRET` was absent locally.
- **`.claude/` is agent-writable** — see `claude-R1-C1`.
- **`gh` is not installed on this machine**, so no GitHub-CLI credential path
  exists for either client; GitHub operations required Stan to use the browser.

These narrow the first "Not yet verified" bullet for Claude Code. Codex's own
stores remain unverified and should not be inferred from these.

## Items I checked and found no fault with

Recorded so a later round does not re-litigate them:

- §7.3 authorization derived from identity and scopes rather than `NODE_ENV` —
  correct, and directly avoids the environment-conditional bypass that caused
  the 2026-08-05 cron exposure.
- §9's typed error taxonomy and the prohibition on returning internal database
  text.
- §12 Phase B's requirement to put migrations on a short-lived branch — matches
  §4 of `docs/multi-agent-concurrency-protocol.md`.
- §14's eval-gate reasoning ("not automatically an Orb-conversation change") —
  consistent with the risk-based gate in `AGENTS.md`.
- §13's `passed 1/1` treatment of the durable workflow versus three runs for
  variable security/replay tests — consistent with the project's verification
  rule.
