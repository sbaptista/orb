## Part 2 — New comments

### `claude-R2-C1` — **Blocker for D8** (scope: §8 `todo_close`, §7.3)

**§8 still asserts unconditional atomicity that §7.3 now says may not hold.**

§7.3, as revised for C5, states that if Knowledge moves to its own store, close
"becomes a durable pending workflow backed by a transactional outbox", and
explicitly warns: *"The plan must not continue calling a separated-store
workflow one transaction."*

§8's `todo_close` contract was not updated and still reads:

> Rules: **one transaction**; first line attribution is added by trusted code;
> no client can bypass the Knowledge entry.

The document therefore contains the exact statement §7.3 forbids. As written, an
implementer reading §8 alone builds a single-transaction close and treats the
outbox provision as optional commentary.

**Recommendation:** restate §8's rule conditionally — one transaction while
todos, audit, and Knowledge are co-resident; durable pending close with
independent receipts if they separate — and make explicit that closure is never
reported complete before both receipts persist. D8 is not safely decidable while
the two sections disagree, because Stan would be deciding a wording that the
contract section contradicts.

### `claude-R2-C2` — **Recommendation** (scope: §15)

**The C1 mitigation covers server-granted authority only; local client
guardrails remain unprotected, and §15 should say so.**

The revision correctly establishes that client-side configuration cannot widen
server-stored scopes. That closes the broker-authority half of the threat. It
does not address the other half: guardrails that exist *only* on the client and
have no server counterpart.

**Evidence (verified, this repository, 2026-08-05):** the `git push` gate is a
`permissions.deny` rule in `.claude/settings.json` — a file the agent can edit.
Nothing server-side enforces it. An agent that modified that file would face no
broker check at all, because pushing is not a broker capability.

The risk is not that the broker's authority leaks; it is that a reader of §5
and §7 may conclude self-configuration is now a solved class of threat. It is
solved for capabilities the broker mediates, and untouched for everything else.

**Recommendation:** add a §15 residual limitation stating that the Capability
Service constrains only operations routed through it, that client-local
guardrails (git push gates, file permissions, tool allowlists) remain outside
its authority, and that those require separate structural enforcement.

### `claude-R2-C3` — **Recommendation on decision readiness** (scope: §16 D2, §3)

**D2 is not decidable on current evidence, and the register does not distinguish
it from decisions that are.**

§6.2 states the transport recommendation "remains pending until client
authentication and credential storage are verified on both Codex and Claude

D2 appears in the register with the same `Pending` status as decisions that only
await Stan's judgement. Deciding D2 now would rest on the untested premise the
document itself flags — which is the failure mode `AGENTS.md` was amended to
prevent, and which this session already produced once (a control recorded as
"Done" that had never been verified).

**Recommendation:** mark evidence-gated rows distinctly — a `Blocked on
evidence` status, or a "Prerequisite" column naming the §3 item each row
depends on. On my reading, **D1 and D3–D16 are decidable on Stan's judgement
today; D2 and the client-storage half of D9 are not.** This is a documentation
change, not a design change.

### `claude-R2-C4` — **Recommendation** (scope: §9)

**The error taxonomy omits `duplicate_suspected`.**

§7.3 introduces a typed `duplicate_suspected` result. §9's enumerated taxonomy —
"unauthenticated, unauthorized scope, invalid input, ambiguous target, not
found, stale target, rate limited, unavailable, and internal failure" — was not
extended. Since §9 reads as the closed list clients program against, an omitted
type invites an implementer to return it as `invalid input` or, worse, to treat
an ambiguous duplicate as success.

**Recommendation:** add `duplicate_suspected` to §9, and state whether it is
retryable (it is not, without human review).

### `claude-R2-C6` — **Recommendation** (scope: §11, §12 Phase E)

**Only Part 2 of the object-capability matrix is named; Part 1 is also
required.**

§11 instructs: "Update Part 2 of `docs/object-capability-matrix.md` with the new
agent-operation flow." `AGENTS.md`'s maintenance rule requires Part 1 as well:
*"New DB table, Orb tool, REST endpoint, or Settings page → add/update the
relevant row and cell in Part 1."* The Capability Service adds a new access
surface for todos, Knowledge, and projects, so Part 1 gains a column or cells
per object.

Phase E's broader "update `docs/object-capability-matrix.md`" is compatible but
less specific than §11's Part 2 instruction, so the narrower text is likely to
win in practice.

**Recommendation:** amend §11 to require both parts. Note the matrix exists
precisely because a capability gap went unnoticed when coverage was checked one
object at a time.

### `claude-R2-C7` — **Question** (scope: §7.2, §8)

**Are tickets deliberately out of scope?**

The word "ticket" does not appear anywhere in the document. Tickets are a
first-class Orb object with their own table, their own conversational tool
(`create_ticket`), a Settings UI, and a documented link to todos via
`ticket_id`. The scope table covers Knowledge, todos, and projects and is silent
on tickets.

Silence is probably deliberate — tickets are reporter-facing and agents filing
them autonomously may be undesirable — but `AGENTS.md` is explicit that a blank
cell must not be assumed intentional.

**Question for Stan/maintainer:** record tickets as an explicit non-goal in §4
with a one-line reason, or as a candidate for a later scope. Either resolves it;
silence does not.
